# 新しいリポジトリのロードマップ

## 前提の確定(2026-09-21・利用者指示。裁定より優先する)

**測る対象は個別銘柄の値動きである。** 注目している個別株が上がるか下がるか、それだけを問う。

- **指数は対象にしない。** TOPIX や業種指数がどう動くかは論点ではない。
  指数を説明変数として使うことは妨げないが、**予測する対象にはしない。**
- **何を指標にするかは開かれた論点である。** 価格系列に限らない。
  財務、需給、マクロ統計、外生的な出来事のいずれも指標の候補になりうる。
  「値動きに限る」は対象の話であって、入力の話ではない。
- 旧リポジトリの案のうち、指数の動きを対象にしていたものは**この前提では最初から対象外**である。

以下の裁定は、この前提のもとで読む。第1段階の参照測定は固定した 2 銘柄の個別株を使うため、
この前提と矛盾しない。第2段階以降で対象量を定めるときは、**個別銘柄の将来の値動き**を
主対比の対象とすること。


**最初に作るのは、実データから登録した差を計算し、判定・報告・終了記録まで残す、一つの参照測定パッケージとする。** その検収後、一件だけ実行可能性を設計し、正式測定する。初期計画はこの3段階で閉じる。

目的は「有効な手法を必ず見つける」ことではない。**誤った量を測らず、測定不能を放置せず、情報不足が分かった設計に計算を再投入しないこと**である。

## 前提と、前回何が壊れていたか

- 新規作成先は `C:/develop/chart_forecasts`。旧リポジトリは恒久凍結を維持する。
- 日本株、NISA成長枠、年間買付額240万円、100株単位、買いのみという指定条件を使う。元本は未定。
- データはJ-Quantsの定額契約から再取得する。
- Claudeが指示・確認・報告、Codexが実装・実行を担当する。統計判定は機械が行う。
- 実行はローカルのみ。GitHub上では何も動かさない。

前回は、問いと計算の対応、判定の伝達、実データの例外処理、事前の識別能力、計算の終了管理が壊れていた。その状態で運営と候補数を増やしたため、測定能力を確認できないまま費用が増えた。

今回の順序は、**全手法に共通する故障を先に除き、次に一件へ資源を投入する価値を検査し、最後に評価結果を開く**という依存関係から決める。

## 第1段階：参照測定パッケージを一つ作る

### 成果物

成果物は **`reference_run` 一つ**。取得、入力検査、差の計算、区間推定、判定、報告、期限停止を一本につなぐ。

以下は実装時の受入インターフェースとする。

```text
python -m chart_forecasts reference --spec specs/reference.json
python -m chart_forecasts verify-reference

specs/reference.json
data/raw/<snapshot_id>/
runs/<run_id>/
  manifest.json
  feasibility.json
  observations.parquet
  result.json
  report.md
  completion.json
state/ledger.sqlite
```

参照測定は、**固定した2銘柄・固定期間について、同日の寄り引け騰落率AとBの平均差**とする。銘柄は成績で選ばず、取得可能性と入力検査への適性で固定する。これは測定器の検収であり、売買手法や収益性の実験には数えない。

A・Bの両方を実際に入力する。Bがゼロだけの検収では、「A−BをAに取り違えた」故障を見逃すからである。

### 完了条件

`verify-reference` が、次の全項目に合格した場合だけ終了コード0を返す。

| 検査 | 合格条件 |
|---|---|
| 問いの固定 | 銘柄、期間、A/B、差の向き、日付対応、単位、集計、欠損処理、推定法、判定境界が仕様に存在し、計算がその仕様を直接読む |
| 差の正しさ | 本体とは別に作った小さな既知解と一致。A/B交換で符号反転し、Bへの定数加算で差が対応して変化する |
| 故障の検出 | A単独への置換、片系列の欠落、日付のずれを意図的に入れた版が不合格になる |
| 判定と報告 | 境界、区間横断、非数、観測不足について固定期待値と一致。報告を再生成すると保存済み報告と一致する |
| 実データ | 新規取得した正常標本では有限の推定値・区間を出す。全日停止・欠損の実例では、事前指定した処理と理由を返す |
| 件数の保存 | 対象件数＝採用件数＋排他的に分類した除外件数。除外元の行・日付まで追跡できる |
| 事前計算 | 本番と同じ推定・判定手順を使う識別能力計算が、既知の簡単なケースと照合できる |
| 終了と再現 | 固定入力・乱数種で数値と判定が一致。期限試験で子孫プロセスも停止し、途中成果と終了理由が残る |

全日停止、休日、取得失敗、理由不明の欠損を混同しない。理由を確認できないものは「不明」と記録する。必要な実例を取得できなければ、その検査は未達とする。

難所で仕様どおり「測定不能」を返すことは例外処理の合格になり得る。ただし、**それだけではこの段階を完了できない。正常な実データによる数値出力も必須**とする。

### 想定所要

**実装・確認14時間、着手から72時間の早い方を上限**とする。取得待ちも72時間に含める。固定標本による検収は10分以内を目標とする。

これは達成予測ではなく、着手前に固定する打ち切り予算である。

### やらないこと

手法探索、資金運用シミュレーター、銘柄ランキング、ダッシュボード、汎用研究基盤、複数提案者、投票、収益性の主張。

## 第2段階：正式測定一件の実行可能性を確定する

### 成果物

**一件の固定仕様と、その仕様を実行してよいかを示す判定ファイル**を作る。

```text
specs/study_001.json
plans/study_001/feasibility.json
plans/study_001/admission.json

python -m chart_forecasts plan --spec specs/study_001.json
```

元本、意味のある効果、同値帯をここで必須入力にする。未入力なら `INPUT_REQUIRED` を返し、正式測定を起動できない。

初回の正式測定は、**価格だけを使い、固定銘柄を100株単位で保有する、月1回判断の単純なルールと現金保有との差**を候補とする。例えば月末終値と過去20営業日の平均価格の比較で翌営業日の保有方針を決める。銘柄、期間、売買条件、費用、約定仮定を仕様に具体化してから検査する。

主評価量は、同じ元本に対する費用控除後の口座収益率差一つに絞る。買えずに現金で待機した期間も含める。この候補が不成立なら、初期計画内で別手法へ次々に乗り換えない。

### 完了条件

`admission.json` が以下をすべて満たした場合だけ `ADMIT` になる。

- 第1段階の検収が、使用するコード版で合格している。
- 元本、必要効果、同値帯、主評価量、比較対象、期限が埋まっている。
- 全注文で100株単位、現金不足なし、売り建てなし、年間買付上限を検査できる。売却額を当年買付累計から差し引かない。
- 停止・欠損時の注文処理、費用、価格調整、情報を利用できる時点が固定されている。
- 開発・設計用データと最終評価用データの区分が記録され、設計処理による評価値へのアクセスが禁止されている。
- 予定期間と取得範囲が一致し、計算量の予算内に収まる。
- **採用する判定手順全体**について、依存を考慮した事前シミュレーションが基準を満たす。

識別能力は次のように定義する。

- 同値帯を `[-δ, δ]` とする。
- 有用な効果の検出は、事前指定した `Δ > δ` における成立確率を評価する。
- 同値判定は、効果ゼロでの成立確率を別に評価する。
- 初期基準は両方80%以上とし、シミュレーション誤差を含む下限値で確認する。
- 推定法の区間被覆率についても、既知の生成過程で事前指定した許容範囲を満たす。
- 同日・同銘柄・保有期間の重なりを扱い、銘柄数×日数を独立標本数にしない。

**判定境界そのものにある効果について、80%の明確な判定を要求しない。** また、検出力だけ高く、誤判定も多い計算を合格させない。

必要な補正は、実際の探索・選択・主張の数から決める。単一の主評価量に不要な補正を重ねず、隠れた試行に必要な補正は省かない。

### 想定所要

**6時間、24時間経過の早い方を上限**とする。事前シミュレーションは1実行30分まで。評価値を見ない成立性の修正は1回まで認める。

これは着手前に固定する打ち切り予算である。

### やらないこと

検出力を通すための必要効果・同値帯の変更、評価結果による銘柄選択、複数案の総当たり、元本未定のままの運用可能性判定。

## 第3段階：一件を正式測定し、結果を閉じる

### 成果物

凍結した仕様に対応する **正式結果パッケージ一件**を保存する。

```text
python -m chart_forecasts run --study study_001
python -m chart_forecasts verify-run --study study_001

runs/<run_id>/
  manifest.json
  observations.parquet
  result.json
  report.md
  completion.json
```

仕様、コード、原本データ、事前計算の識別情報を結び付ける。機械判定を `result.json` に一度保存し、報告はそこから生成する。Claudeの説明文を付ける場合も、機械判定とは別欄にする。

### 完了条件

`verify-run` が次を確認する。

- 実行時の識別情報が、入場判定 `ADMIT` の対象と一致する。
- 登録したA/B・対応日付・差・集計を追跡できる。
- 有限の推定値と区間、観測数、依存を扱う単位、採用率、除外内訳が保存されている。
- 注文・資金・買付上限の全検査に合格する。
- 判定・報告の再生成結果が一致する。
- 固定入力で一度だけ再現確認し、数値と判定が一致する。

統計判定は区間 `[L, U]` と事前の `δ > 0` から排他的に計算する。

| 判定 | 条件 |
|---|---|
| 必要効果を支持 | `L > δ` |
| 不利な効果を支持 | `U < -δ` |
| 実用上同値 | `L >= -δ` かつ `U <= δ` |
| 未確定 | 有効な区間があるが、上記のいずれでもない |

区間を計算できない場合は、統計判定を付けず測定障害とする。

**未確定でも、正しい数値測定としてこの段階を完了できる。ただし「判断までできる土台」の成立には数えず、探索拡張へ進まない。** 有効な効果の支持だけを成功条件にはしない。

### 想定所要

**5時間、24時間経過の早い方を上限**とする。本測定は60分まで、再現確認も60分まで。

第1段階の着手から、**累計25時間または120時間経過で初期計画を閉じる**。これらは着手前に固定する打ち切り予算であり、自動延長しない。

### やらないこと

評価後の条件調整、都合のよい期間の切り出し、同じ結果の再計算による測定件数の水増し、実発注、複数手法への拡張。

## 「土台が動く」の定義

状態を一つの「成功」にまとめない。

| 状態 | 機械的な定義 |
|---|---|
| 実行成立 | 期限内に必須成果物がそろい、検証できる |
| 測定成立 | 登録量の数値・区間を算出し、仕様一致検査に合格する |
| 判定成立 | 測定成立に加え、事前規則による必要効果・不利・同値のいずれかになる |

第1段階の合格は「測定器の検収完了」。**正式測定で測定成立と判定成立を一件得て、初めて「判断までできる土台が動いた」と記録する。**

停止記録、難所での適切な拒否、参照測定を、この正式実績に混ぜない。一方、未確定を無効や同値へ読み替えることも禁止する。

## 運営の仕組みと、最初の手法の決め方

**仕様固定・証跡・停止台帳は第1段階から作る。** 測定器の入力と終了管理に必要なためであり、後から追加する運営制度ではない。正式な事前登録は、第2段階終了時の仕様・コード・事前計算のローカルGitへの固定で行う。

Claudeは参照検査の期待値と正式仕様を書き、Codexが実装する。Claudeが確認して指摘した不備は、修正と機械検査へ変換する。**「Claudeが問題なしと言った」は完了条件にしない。** 期待値や受入条件を実装に合わせて変更した場合、以前の合格記録は失効させる。

最初の正式手法はClaudeが一件に具体化し、Codexが取得・実装・識別能力を検査する。利用者が決めるのは元本と実用上必要な差である。これは入力値の決定であり、完成判定の代行ではない。

公表済みアノマリーの再現は必須にしない。原研究との照合が別の作業になるうえ、指定された資金・売買条件に適合するとは限らない。初回は、期待収益の評判より**仕様の短さ、時点の明確さ、注文と損益の追跡可能性**を優先する。

複数提案者、投票、監査委員会は初期計画に導入しない。初期計画終了後も自動追加しない。測定・判定成立を得た後、候補不足が実際の停滞原因になった場合にだけ別途検討する。投票を統計的な真偽判定には使わない。

## 打ち切り条件

すべての正式実行をローカル台帳に登録し、起動コマンドが次の条件を確認する。

| 検出条件 | 自動動作 |
|---|---|
| 段階別・全体の時間上限超過 | 子孫プロセスを停止し、新規実行を拒否 |
| 必須入力なし、事前計算未作成・基準未達 | 本評価を起動しない |
| 同じ受入検査が修正後も失敗 | 第1段階を停止 |
| 同じ技術障害コードが2回発生 | 該当処理と本評価を停止 |
| 評価開始後に仕様・入力・コードが変更 | 同一実験としての再判定を拒否 |
| 正式結果が未確定 | 同一仕様・同一データによる追加評価を拒否 |
| 正式測定2件連続で未確定 | リポジトリ全体の新規仮説投入を停止 |
| 必須結果ファイル欠落 | 実行障害として記録し、成功件数を増やさない |

初期計画では正式測定は一件だけなので、未確定ならそこで閉じる。「2件連続」は、後日別途認めた研究にも引き継ぐ共通停止条件である。名前・ブランチ変更、再現確認、参照測定では連続数をリセットしない。

再開には、原因コード、変更する部品または増える情報量、それを検証する事前検査、新しい予算を記録する。旧実験の上書きや期限の自動延長は認めない。追加情報も設計改善もない場合、その問いを終了する。

予算は開始時に絶対時刻へ変換する。処理時間は子プロセスの実績を集計し、担当者の時間申告だけに依存させない。

## 前のリポジトリから持ち出すもの

持ち出す対象は次に限定する。

1. **期限監視の二つのスクリプトを再利用候補として扱う。**  
   `.claude/scripts/deadline_watch.py` と `run-with-deadline.sh` は、新環境で子孫プロセス停止・終了状態保存を検収してから採用する。シェルの互換性がなければ、動作要件を引き継いで実装し直す。

2. **依頼文に残された7件の失敗事実を、新規の受入検査へ変換する。**  
   失敗記録そのものを研究成果には数えない。

破棄済みデータ・調査・測定成果を復旧せず、旧実装や運営規程も一括移植しない。旧リポジトリを再調査しなければ進められない構成にはしない。

## 3 名の回答からの取捨

| 裁定 | 理由 |
|---|---|
| **採用：一つの参照測定を最初に通す** | 共通の故障を手法の良否から分離でき、後続の一件にもそのまま使える |
| **採用：実行・測定・判定の区別** | 正常終了や停止記録を、判断できた実績へ昇格させないため |
| **採用：既知解、意図的故障、実データによる検収** | 仕様ハッシュや合成データの正常系だけでは、誤配線と現実の欠損処理を検出できない |
| **採用：元本を確定してから正式な運用比較へ進む** | 記述的な価格差を一件測ってから資金制約へ作り直すより、最初の正式測定を利用目的に結び付けられる |
| **退ける：第1段階から売買やランキングを実装する** | 注文・資金・選択の分岐が増え、差の測定器を検収する目的に不要な依存が入る |
| **退ける：検出力報告が存在すれば実行可とする** | ファイルの存在は識別能力の確認にならない。実際の判定法に対する数値基準が必要 |
| **退ける：初期計画の第4段階として探索を広げる** | 一件の結果を見る前に探索拡張を予定すると、未確定でも候補投入を続ける余地が残る |
| **退ける：技術的完走が一定件数に達したら複数提案者を追加する** | 完走数だけでは判定能力も、提案者を増やす必要性も示せない |
| **退ける：正式結果が未確定なら技術的完了まで否定する** | 測定の正しさと情報不足を混同する。ただし判断能力の成立や拡張は認めない |

## 推測

- **25時間・120時間、検出力80%、技術障害2回、未確定2件**は、今回の記録から最適値を導いたものではない。際限ない継続を防ぐ初期予算案である。
- 時間内の完成は、認証が利用でき、契約範囲に必要なデータと難所の実例があることを仮定している。
- 単純な月次価格ルールは追跡しやすい候補だが、有用な効果や十分な識別能力がある根拠はない。第2段階で不成立となる可能性がある。
- 識別能力は依存構造や分布の仮定に左右される。事前計算の合格は、現実の明確な判定を保証しない。
- 保証できる範囲は、検査済みの経路で測定を行い、成果と終了理由を残し、既知の失敗を無条件に繰り返さないことまでである。有限データから必ず明確な結論を出すことは、完了条件に置かない。
